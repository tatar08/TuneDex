# TuneDeck API (`services/api`)

NestJS + PostgreSQL backend. This folder started as COL-01 from [Doc 19](../../Docs/19-Claude-Codex-Collaboration.md) and now holds health probes, account settings, the device registry, staff roles and the radio station catalog. It is self-contained (own `package.json` and lockfile) so it does not touch root manifests that COL-00 will define.

## What it does

| Route | Behavior |
|---|---|
| `GET /health/live` | 200 while the process runs |
| `GET /health/ready` | 200 when PostgreSQL answers, else 503 (also 503 while shutting down) |
| `GET /v1/me/settings` | The signed-in account's settings with `ETag: "<revision>"`. New accounts get defaults at revision 0 |
| `PATCH /v1/me/settings` | Partial update. Requires `If-Match: "<revision>"`; stale → 412 `REVISION_MISMATCH` with `currentRevision` |
| `GET /v1/me/devices` | The account's devices plus the current `settingsRevision` and `serverObservedAt`, active first, most recently seen first. Each device carries its `overrides` and `preferencesRevision` |
| `GET/PUT /v1/me/devices/{deviceId}/preferences` | Doc 17 per-device overrides. Body `{ "overrides": { ... } }` with only the account setting keys (theme, language, cellular policy); `{}` clears them. `If-Match` is the preferences revision (`0` for the first write), 412 `REVISION_MISMATCH` otherwise. The answer carries `overrides`, `effective` (account settings with the overrides applied) and `accountRevision`. Another account's or an unknown device is 404; a revoked device 403 `DEVICE_REVOKED`. Removed with the device |
| `PUT /v1/me/devices/{deviceId}` | The phone app's check-in: registers the device on first call, then records platform, OS major, app build and the settings revision it has applied |
| `DELETE /v1/me/devices/{deviceId}/session` | Revokes a device. Needs a sign-in within the last 5 minutes (`auth_time`), else 401 `REAUTH_REQUIRED`. The first revoke is audited as `device.revoke`. The device's Keycloak session is then ended too (see **Device sessions at Keycloak**) |
| `GET /v1/me` | Signed-in user. `{ userId, email, status, createdAt }`: the account code customers give support (looked up in `/admin/users`). The email comes from the access token's `email` claim and is stored on sign-in (cleared when the account is purged). No subject or roles |
| `POST /v1/sync/push` body `{ deviceId?, changes: [...] }` | Account sync (Doc 06), R1 scope: station favorites. Up to 100 changes `{ changeId, entityId, type: "favorite", op: "upsert"\|"delete"\|"restore", baseRevision, value: { stationId, order } }`, applied in order, each with its own result: `applied` (new `revision`), `conflict` (`exists`, `not_found`, `revision_mismatch`, `deleted`, `not_deleted`, `station_already_favorite`, with the server's `current` state) or `rejected` (`unknown_station`, `change_id_reused`). `baseRevision` 0 creates; otherwise it must equal the current revision. A delete wins over stale updates; only `restore` naming the tombstone revision brings an entity back, and a create can never reuse a deleted id. A replayed `changeId` returns its first result. One live favorite per station. A revoked `deviceId` → 403 `DEVICE_REVOKED` |
| `GET /v1/sync/pull?cursor=&limit=&deviceId=` | Changes and tombstones after the cursor, oldest first (limit 1–100, default 50), with the next `cursor` and `hasMore`. No cursor = full reconciliation. Tombstones and replay records are kept 90 days; a cursor from before the account's purged horizon → 410 `SYNC_RESET_REQUIRED` (pull again without a cursor). Push and pull with `deviceId` record the device's `lastSyncedAt` |
| `GET /v1/me/favorites` | The live favorites with their revisions, in order (for the web page) |
| `POST /v1/billing/verify` body `{ store: "apple", signedTransaction }` or `{ store: "google", productId, purchaseToken }` | The app sends the store's proof after a purchase or restore. Apple: the JWS is verified offline against the pinned Apple root (chain, validity, Apple marker extensions, ES256), then bundle id, Pro product id and environment are checked. Google: the Play Developer API is asked as the service account, then the purchase is acknowledged after it is stored. `appAccountToken` (Apple) or `obfuscatedExternalAccountId` (Google) must be set to the account id (`PURCHASE_INVALID` `account_unbound` when missing, `account_mismatch` when another live account); one bound to a deleted account can be restored onto the current one. A refund or revocation the store reports before the purchase is first verified leaves a tombstone (digest only, `purchase_revocations`), so verifying the old signed transaction later still gives `revoked`. One purchase belongs to one live account (409 `PURCHASE_CONFLICT`); a purchase of a deleted account moves to the account restoring it. A revoked purchase stays revoked. Store not configured or unreachable → 503 and nothing new is granted. Audited `purchase.verified` / `purchase.pending` / `purchase.revoked` |
| `GET /v1/me/entitlements` | `{ pro: { apple, google }, purchases }`: Pro per store (`verified`, `pending`, `revoked`, `none`), store-scoped in R1 |
| `POST /v1/webhooks/apple` | App Store Server Notifications V2 (`signedPayload`, verified like a transaction). `REFUND` and `REVOKE` revoke the purchase; `REFUND_REVERSED` gives it back when Apple's transaction no longer shows a revocation (audited `purchase.restored`). Redeliveries are recognized by `notificationUUID`. Notifications from an environment not in `APPLE_ENVIRONMENTS` are acknowledged and ignored |
| `POST /v1/webhooks/google` | Play real-time developer notifications via Pub/Sub push, authenticated by Google's OIDC token (audience and service account from config). Voided purchases are revoked; a pending purchase that completes is re-checked with the API, verified and acknowledged. A store that is not configured answers its webhook 401, like a bad signature; handled notification ids are forgotten after 30 days |
| `POST /v1/me/exports` | Doc 17 export job: needs a sign-in from the last 5 minutes (else 401 `REAUTH_REQUIRED`). 202 `{ id, status: "pending", requestedAt, readyAt, expiresAt }`; asking again while one is being built returns that one. Built in the background into `account_exports` (migration 017); a failed build follows the shared retry policy (see **Background jobs**) and after 5 attempts is dead-lettered, which the user reads as `failed`. It is deleted 24 hours after the request, or with the account; audited `account.export` |
| `GET /v1/me/exports/{id}` | The job's status, the account's own only (404 otherwise). Read-only: reading never creates a link |
| `POST /v1/me/exports/{id}/link` | When the job is `ready`: 201 `{ path, expiresAt }`, a download link valid for 15 minutes, to prefix with the API base URL; each call replaces the previous link. 409 `EXPORT_NOT_READY` otherwise |
| `GET /v1/export-downloads/{token}` | The export file (`Content-Disposition: attachment`), no sign-in needed: the unguessable link is the permission, so a phone can open it in a browser. Expired or replaced links are 404. Limited per client address like the public catalog; only a digest of the link is stored, and the route is logged without the token |
| `GET /v1/me/export` | The same data built on the spot; needs a sign-in from the last 5 minutes. Kept for existing clients; new clients use `POST /v1/me/exports`. Audited `account.export` |
| `POST /v1/me/support-access/codes` | Doc 17 support access, customer side: a one-time code `{ code: "ABCD-EFGH", expiresAt }`, valid 60 minutes, to read out to support. A new code replaces an unused one. Only a digest is stored (`support_access_codes`, migration 019); audited `support.code_created` |
| `GET /v1/me/support-access`, `DELETE /v1/me/support-access/{id}` | The accesses the customer has given that are still running, and withdrawing one (204, audited `support.access_revoked`) |
| `POST /v1/admin/users/{userId}/diagnostics/access` body `{ code, reason }` | `support` or `admin`. Enters the customer's code (any case, dash optional). Grants **this staff member only** 7 days of access to that customer's diagnostic reports (Tar's choice, 2026-10-04). A wrong, used, replaced, expired or other customer's code is 404 and audited `support.access_refused`; success is audited `support.access_granted` with the reason. The lookup's `diagnostics.access` shows the caller's running access |
| `GET /v1/admin/users/{userId}/diagnostics` | `support` or `admin` with a running access, else 403 `SUPPORT_ACCESS_REQUIRED`. The 20 most recent reports with their events, without event or session ids. Every read is audited `support.diagnostics_read`. Access ends after 7 days, when the customer withdraws it, or with the account |
| `DELETE /v1/me` (also `DELETE /v1/me/account`) | Starts account deletion (sign-in within 5 minutes, else 401 `REAUTH_REQUIRED`). 202 with a ticket. The account is locked (403 `ACCOUNT_DELETING`) and every device signed out at once; a purge first deletes the Keycloak user (see **Account deletion at Keycloak** below), then removes settings, devices, favorites and sync records, diagnostics and staff roles and leaves a pseudonymous `users` tombstone with the OIDC subject cut. The ticket reads `completed` only after both. Failed purges follow the shared retry policy and are dead-lettered after 5 attempts; the account stays locked meanwhile (see **Background jobs**). Tokens from sign-ins made before the request are refused |
| `GET /v1/account-deletions/{ticket}` | Public progress: `deleting`, `completed` or `failed` (retrying or dead-lettered), with the 30-day deadline. Rate limited per client address |
| `GET /v1/me/staff` | The caller's current staff roles (empty for customers), `mfa` (whether this Keycloak session signed in with MFA, see **Staff sessions**) and `rolesVersion`, a digest that changes whenever a role is granted or revoked, so the console can end a staff web session after a role change |
| `POST /v1/diagnostics/batches` | Signed-in user, from one of their registered, non-revoked devices. Opt-in upload: `consent: true`, `batchId`, `deviceId` and 1-100 events in the Doc 07 schema (allowlisted names and fields only; unknown fields are refused). Up to 128 KiB, 10 batches a minute per device. Retries are safe: a repeated `batchId` returns the first result and repeated `eventId`s are skipped |
| `GET /v1/me/diagnostics`, `GET /v1/me/diagnostics/{id}`, `DELETE /v1/me/diagnostics/{id}` | The owner's own reports (summary, full events, delete). Reports are deleted after 7 days |
| `GET /v1/catalog/radio?cursor=&limit=` | Public, no sign-in. Published, enabled stations with current rights; opaque cursor, `limit` ≤100, weak ETag and `If-None-Match` → 304, `Cache-Control: public, max-age=300` |
| `GET /v1/directory/radio?q=&country=&language=&tag=&limit=&offset=` | Public, no sign-in. Search of the Radio Browser community directory through our server (Tar, 2026-10-05): https streams in mp3/aac/hls only, the same stream rules as our catalog, cached 10 minutes (served up to an hour old while Radio Browser is down), blocked stations removed, search text never logged. Community data, not our catalog: the apps add a station to the user's own list only when the user picks it. Off (503 `DEPENDENCY_UNAVAILABLE`, `not_configured`) unless `RADIO_BROWSER_BASE_URL` is set to one Radio Browser server, e.g. `https://de1.api.radio-browser.info`; the app switch is `features.radioDirectory` |
| `GET /v1/admin/stations`, `GET /v1/admin/stations/{id}` | `catalog_editor` or `admin`. Draft, published snapshot, status, stream `health` (`unknown`/`ok`/`failing`/`suspect`, per region), a `rights` summary (`current`/`missing`/`territory`/`not_yet_valid`/`expired`, expiry, reference, `liveUntil`) and the reasons the caller could not publish right now. The list takes `q` (part of the name, any case) and `status` |
| `GET /v1/admin/stations/summary` | `catalog_editor` or `admin`. `{ total, visible, pending, drafts, disabled }` in one query, for the console header; `visible` is what the public catalog serves now |
| `GET /v1/admin/directory/blocks`, `POST /v1/admin/directory/blocks`, `POST /v1/admin/directory/blocks/{id}/remove` | `catalog_editor` or `admin`. Take a community station (`kind: station`, Radio Browser id) or a whole stream host and its subdomains (`kind: host`) out of the directory search, e.g. on a rights holder's complaint, and lift it again; each needs a reason and is audited (`directory.block.add` / `.remove`). Stations users already added stay in their lists |
| `POST /v1/admin/stations`, `PATCH /v1/admin/stations/{id}` | `catalog_editor` or `admin`. Edits the draft only; PATCH needs `If-Match` |
| `POST /v1/admin/stations/{id}/publish` | `admin`, with `If-Match` naming the reviewed revision and a `reason`. Needs recent MFA (see **Recent MFA for staff**) |
| `GET /v1/admin/stations/{id}/health` | `catalog_editor` or `admin`. The last 20 stream checks, newest first: region, time, result code, HTTP status, latency. No URLs |
| `POST /v1/admin/stations/{id}/check` | `catalog_editor` or `admin`. Checks the published stream now (the draft stream before the first publish). One manual check per station per minute (429 `CHECK_TOO_SOON`); audited as `station.check` |
| `POST /v1/admin/stations/{id}/disable`, `/enable` | `admin`, with a `reason`. Hides or restores the station in the public catalog at once |
| `GET /v1/admin/stations/{id}/rights` | `catalog_editor` or `admin`. The station's rights records, newest first: holder, basis, reference, territories, `validFrom`, `expiresAt`, `status` (`active`/`revoked`) and `effectiveStatus` (`active`/`scheduled`/`expired`/`revoked`), who created or revoked it, and the private `evidenceRefs` (opaque storage keys, only in this response) |
| `POST /v1/admin/stations/{id}/rights` body `{ holder, basis, reference, territories, validFrom?, expiresAt?, evidenceRefs? }` | `catalog_editor` or `admin`. `territories` are ISO 3166 alpha-2 codes; `validFrom` defaults to today (UTC); `expiresAt` is valid through that whole day (UTC), `null` for no end; up to 10 evidence keys, never URLs. Takes effect at once for the publish gate and the public catalog. 201 without the evidence keys; audited as `rights.add` (no holder, no evidence keys) |
| `POST /v1/admin/stations/{id}/rights/{recordId}/revoke` body `{ reason }` | `catalog_editor` or `admin`. Without another active, current record for the station's country the station leaves the public catalog at once. 409 `RIGHTS_ALREADY_REVOKED` the second time; audited as `rights.revoke` with the reason |
| `GET /v1/admin/stations/{id}/history?cursor=&limit=` | `catalog_editor` or `admin`. The station's version history from the audit trail (`station.*` and `rights.*`), newest first: action, actor subject, reason, revision, changes. Cursor pages of 50, at most 100 |
| `GET /v1/admin/logs?from=&to=&severity=&service=&build=&eventCode=&requestId=&traceId=&errorCode=&status=&limit=&cursor=` | `operator` or `admin`. Newest first; window ≤24 hours (default last hour), `limit` default 50 and ≤100 (Doc 17 initial limits), opaque cursor. `traceId` is 32 lowercase hex. Every search is written to `audit_events` before results are returned |
| `POST /v1/admin/logs/export?<same filters>` body `{ reason }` | `operator` or `admin`, with MFA in the last 5 minutes (else 401 `MFA_REQUIRED`). The search as CSV (UTF-8 BOM, formula-like cells neutralised), at most 10,000 lines, else 400 `too_many_rows`; same 24-hour window. Audited `logs.export` with the reason, filters and row count (never the lines) |
| `GET /v1/admin/audit?from=&to=&actor=&action=&targetType=&targetId=&requestId=&includeReads=&limit=&cursor=` | `auditor` or `admin`. Newest first; window ≤90 days (default 7), `limit` ≤100, opaque cursor. `actor` takes an OIDC subject or `operator:<label>`; `action` takes a full action or a family (`station`). Each read writes an `audit.search` row; search rows are hidden unless `includeReads=1` |
| `POST /v1/admin/audit/export?<same filters>` body `{ "reason" }` | `auditor` or `admin`. The same search as CSV (UTF-8 with BOM, formula-like cells prefixed with `'`), at most 10,000 rows (more is 400 `too_many_rows`). The reason (10–500 characters) is recorded with the filters and row count as `audit.export`. Needs recent MFA |

Aggregates only: request count, 5xx/4xx, p50/p95 latency and per-bucket bars from stored request logs, station health counts, account-deletion queue, opt-in app diagnostics (`clients`: per event the attempts, failures (any `resultCode`) and devices, the 10 most common failure codes and the 5 busiest builds per platform), and incidents (5xx ≥ 5% with ≥ 50 requests, failed (retrying or dead-lettered) or late deletions, suspect stations, stalled checker, no traffic for 15 min, plus every open alert) |
| `GET /v1/admin/metrics?from&to&bucket=1h\|1d&method&route` | `operator` or `admin`. Default the last 24 hours by hour; hourly over at most 14 days, daily over at most 90. A client that sends no platform only gets releases aimed at every platform and build. The signed payload also carries `environment` and `targets` |

- **Auth:** every `/v1` call except the public catalog needs an OIDC bearer token verified against the JWKS for issuer, audience, expiry and an asymmetric algorithm. The account comes from the token `sub`, never from the body or URL. Unknown key or bad token → 401; key set unreachable → 503 (fails closed). Accounts in `deleting`/`disabled` status → 403. There is no dev bypass; fake identity exists only in `test/`.
- **Settings allowlist** (proposal, see `openapi.proposal.yaml`): `theme` system/light/dark, `language` th/en, `cellularPolicy` allow/wifi_only. Defaults: system, th, allow.
- **Devices:** `deviceId` is a UUID the app generates once per install. Check-ins accept only `platform` (ios/android), `osMajor`, `appBuild` and `appliedSettingsRevision`; no device name, model or advertising id is stored. An applied revision higher than the server's → 400; a late, older report never moves the applied revision backwards. A revoked device's check-in → 403 `DEVICE_REVOKED` (the app should sign out). At most 20 active devices per account → 409 `DEVICE_LIMIT`. Device ids are scoped per account, so another account's id is simply not found.
- **Staff roles** (`support`, `catalog_editor`, `operator`, `admin`, `auditor`) live in the database and are read on every staff request, so a revoke takes effect on the next call. There is no self-service grant: an operator runs `DATABASE_URL=… npm run staff -- grant <oidc-subject> <role> --by <name> --reason "<why>"` (also `revoke`, `list`). Each grant and revoke is audited. A grant needs the person to have a one-time code (TOTP) at Keycloak already: with the Keycloak admin client configured the CLI checks their credentials and refuses (exit 3) otherwise; without it (local dev) it warns and grants. **Pinned one-time codes:** Keycloak 26 lets a password-only sign-in enroll a new code, so the grant also records the codes the person has (`staff_mfa_pins`, migration 033), and every `/v1/admin` request answers 403 `STAFF_MFA_CHANGED` while the account holds a code that was not pinned (checked against Keycloak at most once a minute per Keycloak session, so a new session is always checked; 503 `DEPENDENCY_UNAVAILABLE` if Keycloak cannot be asked, never a pass). A grant to someone whose codes changed since the pin is refused (exit 4). Staff with roles from before pins existed get their codes pinned on their first MFA request (`staff_mfa.pin` by `system:staff`). After a legitimate change (new phone, reset), check with the person, then `npm run staff -- pin-mfa <oidc-subject> --by <name> --reason "<why>"` (audited). Skipped in dev when MFA is not required or the admin client is not configured.
- **Station catalog:** every station has a draft and, once approved, a published snapshot; only the snapshot reaches the apps. Two-person rule: anyone who changed the draft since its last publish cannot publish it. Publishing also needs an active rights record whose territories include the station's country, valid today (`validFrom` reached, `expiresAt` not passed); otherwise the blockers are `rights_missing`, `rights_territory`, `rights_not_yet_valid` or `rights_expired`. The emergency publish skips only the second admin, never the rights. Adding or revoking a record recomputes `radio_stations.rights_expires_at` (the end of the latest current covering record, now when there is none), so a revoke hides the station at once and the station drops out of the public catalog on its own when its last record expires. A record that only becomes valid later does not bring a station back by itself on that day; adding or revoking any record, or publishing, recomputes it. Stream URLs must be `https://` on port 443 with a public host name (no IP literals, `localhost` or internal suffixes, no credentials). The API never fetches them; health checks belong to the future worker.
- **Operational logs:** every redacted log line still goes to stdout, and is also buffered and written to `operational_logs` in batches off the request path (health probes excluded). If the database is unavailable the batch is dropped and a `LOG_STORE_DROPPED` count goes to stdout; requests are never slowed or failed by logging. Lines older than 14 days are deleted hourly in small chunks.
- **Stream health (Doc 17 catalog checker):** with `STATION_CHECK_ENABLED=true` the API checks every published, enabled station every `STATION_CHECK_INTERVAL_MIN` minutes (default 15, plus up to 10% jitter), four at a time, and only one instance runs a pass (advisory lock). Each check is HTTPS on 443 only; every DNS answer and every redirect target must be a public address (loopback, private, link-local, metadata, CGNAT, documentation, multicast and IPv6 ULA/link-local/mapped/NAT64 are refused), the connection goes to the address that was checked so DNS cannot rebind, at most 3 redirects, 10 s, and only the headers and first bytes are read. Results go to `station_health` as codes (no URLs) tagged with `STATION_CHECK_REGION`, kept 30 days. Three failures in a row since the last publish make a station `suspect` for an admin to review; nothing is disabled automatically. **Separate checker (Doc 17 egress):** `npm run checker` runs the checks as their own process with no HTTP server. With `STATION_CHECK_RUNNER=worker` on the API (and the same `STATION_CHECK_*` keys on both), the API never probes a stream: scheduled passes run only in the checker, and a staff "check now" becomes a row in `station_check_requests` (migration 027) that the checker answers within a second; the API waits up to 15 s, else 503 `CHECKER_UNAVAILABLE`. Only the checker then needs outbound HTTPS. The default `api` keeps everything in the API process.
- **Rate limits (Doc 17 initial limits):** a signed-in caller gets 120 reads and 30 writes a minute; the public catalog gets 60 a minute per client address. Counters are per minute in PostgreSQL (`rate_limit_counters`, unlogged), so every instance shares them; client addresses are stored only as a short hash. Over the limit is 429 `API_RATE_LIMITED` with `Retry-After`. Health probes and rejected sign-ins are not counted. If the counters cannot be written the request goes through and `RATE_LIMIT_UNAVAILABLE` is logged. Set `TRUST_PROXY_HOPS` to the number of proxies in front of the API so the client address comes from their `X-Forwarded-For`.
- **Idempotency-Key (Doc 17):** any signed-in `POST`/`PUT`/`PATCH`/`DELETE` may carry an `Idempotency-Key` header (8–128 characters of `A-Z a-z 0-9 _ . : -`, e.g. a UUID). The same account, method, path and key then runs at most once for 24 hours: a repeat with the same body and `If-Match` gets the first answer again (same status, body, `ETag` and `Location`) with `Idempotent-Replayed: true`; a repeat with a different body is 409 `IDEMPOTENCY_KEY_REUSED`; a repeat while the first is still running is 409 `IDEMPOTENCY_IN_PROGRESS` with `Retry-After: 1`. Only successful answers are kept; an error frees the key so the client can retry with it. Only digests of the key and request are stored (`idempotency_keys`, migration 016), expired keys are pruned hourly, and an account's keys are removed when it is purged. If that table cannot be reached the request is 503, not run unprotected. Requests without the header behave as before, except `POST /v1/me/exports` and `DELETE /v1/me`, which require it (428 `IDEMPOTENCY_KEY_REQUIRED`). A retried `DELETE /v1/me/account` after the first succeeded gets 403 `ACCOUNT_DELETING` (the account is locked at once), not the ticket again. `POST /v1/sync/push` also keeps its own per-change idempotency.
- **Account deletion at Keycloak** (Tar's decision A, 2026-10-04): the purge deletes the user at Keycloak (`DELETE /admin/realms/<realm>/users/<sub>`) before touching local data, using the service account of a confidential client (`KEYCLOAK_ADMIN_CLIENT_ID` / `KEYCLOAK_ADMIN_CLIENT_SECRET`, client-credentials grant). The realm and URLs come from `OIDC_ISSUER`. A user already gone (404) counts as deleted, so retries are safe; any other failure leaves the account untouched in `deleting` and is retried, logged as `ACCOUNT_PURGE_FAILED` with `errorCode` `IDP_TOKEN_FAILED` or `IDP_DELETE_FAILED` and the HTTP status only. The `account.deleted` audit records `idpUser`: `deleted`, `already_gone` or `not_configured`. Required outside dev; in dev without it the Keycloak user is kept and `IDP_USER_KEPT` is logged. Keycloak setup: create a confidential client with only "Service accounts" enabled and give its service account the `realm-management` role `manage-users` (Keycloak has no narrower built-in delete-only role; where the Keycloak version supports fine-grained admin permissions, limit it to deleting users). This assumes the realm serves TuneDeck only; a shared realm would delete the person's other logins too.
- **Store purchases (Doc 11, ADR-12):** only a SHA-256 digest of Apple's `originalTransactionId` or Google's `purchaseToken` is stored (`purchases`, migration 013), never receipts or identifiers, and they are never logged. Each store is off until configured: Apple needs `APPLE_BUNDLE_ID`, `APPLE_ROOT_CA_PEM` (Apple Root CA - G3, from apple.com/certificateauthority), `APPLE_PRO_PRODUCT_IDS` and optionally `APPLE_ENVIRONMENTS` (default `Production`); Google needs `GOOGLE_PLAY_PACKAGE_NAME`, `GOOGLE_PLAY_PRO_PRODUCT_IDS`, `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` (a service account with Play Console financial access), `GOOGLE_PUBSUB_PUSH_AUDIENCE` and `GOOGLE_PUBSUB_PUSH_SERVICE_ACCOUNT`. Staff cannot grant Pro. When an account is deleted its purchase rows are kept (only the digest, status and dates, no personal data), so a refund or chargeback can still be matched and the same store account can restore Pro on a new account (decided by Tar, 2026-10-05).
- **Device sessions at Keycloak:** a device reports its token's Keycloak session id (`sid`) when it checks in (`devices.idp_session_id`, migration 014). Signing the device out from the web then ends that session at Keycloak (`DELETE /admin/realms/<realm>/sessions/<sid>`, and again with `isOffline=true` for offline tokens), so its refresh token stops working. From the moment of the revoke the API also refuses any token carrying that session id for that account (403 `DEVICE_REVOKED`), so the sign-out holds even while Keycloak is unreachable; failed calls are logged as `IDP_SESSION_END_FAILED` and retried per the shared retry policy (dead-lettered after 5 attempts, listed on `/v1/admin/jobs` as `idp_session_end`) for devices signed out in the last 30 days. Other devices and the web session are not touched. It uses the same `KEYCLOAK_ADMIN_CLIENT_*` service account as account deletion (`manage-users` covers sessions). Devices that have not checked in since this release have no session id yet; their sign-out works as before (refused by device id on the API, refresh token valid until it expires).
- **Staff sessions (Doc 17):** every `/v1/admin/*` route needs a Keycloak session that signed in with MFA (an `acr` in `STAFF_MFA_ACR`) within the last 12 hours; the API remembers that session's `sid` (`staff_mfa_sessions`, migration 023) so later tokens of the same session pass. Otherwise 401 `MFA_REQUIRED` with `details.scope: "session"` and `maxAgeSeconds: 43200`. Off in dev without `STAFF_MFA_ACR`. Rows are deleted with the account.
- **Database and shutdown:** the pool holds `DB_POOL_MAX` connections (default 20, 2–200); every statement stops after 5 s, which answers 503 and logs `DB_QUERY_TIMEOUT` with the route (a slow query, not an outage). On SIGTERM/SIGINT `/health/ready` turns 503 for `SHUTDOWN_DRAIN_MS` (default 5000) before the server, workers and pool close; a second signal exits at once.
- **CORS:** off unless `CORS_ALLOWED_ORIGINS` lists exact origins (comma-separated, `https://` only, `http://` allowed in dev). Credentials are never allowed cross-origin; the console calls the API from its server (BFF), so it needs no entry.
- **Paging:** list routes take `limit` (default 50, at most 100) and return an opaque `nextCursor` (keyset, so pages stay stable while rows change): admin stations, devices, diagnostics, audit and logs.
- **Recent MFA for staff (Doc 17):** station publish, config stage, config publish, config rollback, audit export and log export need an access token whose `acr` is one of `STAFF_MFA_ACR` and whose `auth_time` is within 5 minutes, else 401 `MFA_REQUIRED` (`details.maxAgeSeconds: 300`). Reading is unaffected. `STAFF_MFA_ACR` is required outside dev; in dev without it the check is off. Keycloak setup: an authentication flow with a step-up level that requires OTP or WebAuthn, mapped to the acr value(s) listed here (Realm settings → ACR to LoA mapping), and the console's `OIDC_MFA_ACR` set to the same value.
- **Alerts (Doc 17):** once a minute, on one instance, the API checks:
  - API 5xx above 2% of at least 100 requests in 5 minutes (critical);
  - p95 latency above 1 s over at least 20 requests in 10 minutes (warning);
  - failed account deletions, retrying or dead-lettered (critical), and deletions older than 25 days (critical);
  - Doc 17 "queue oldest > 5 min", per queue: a job due (requested, or its backoff over) for more than 5 minutes and not yet run, as `account_deletion_stuck`, `account_export_stuck` and `idp_session_end_stuck` (warning; the last only when a Keycloak admin client is configured);
  - Doc 17 "dead-letter > 0": `job_dead_letter` (critical), across all queues;
  - a stream checker that stopped running (warning, only when the checker is on);
  - Doc 14 rights expiry: `station_rights_expiring` (warning) while any visible station's rights end within 14 days; it resolves once a renewed record moves the end out (the message gives the count, never the station).
  - Doc 17 "no successful backup for 24 hours": `backup_stale` (critical) when the newest run `infra/backup/backup.sh` recorded in `backup_runs` is 26 hours old or more. Silent until the script has recorded a first run, so a deployment relying only on the provider's backups never sees it.
  
  Too little traffic reads "unknown" and neither opens nor closes an alert. Each occurrence is a row in `alerts` (migration 015). It is logged as `ALERT_FIRING` / `ALERT_RESOLVED` with the rule in `errorCode`, shown on `/admin/overview` with its start time, and, when `ALERT_WEBHOOK_URL` is set (https, Slack- or Discord-compatible, a secret that is never logged), posted as a Thai chat message. Failed posts are retried on the next run (`ALERT_NOTIFY_FAILED`). Messages carry aggregates only. `ALERTS_ENABLED=false` turns the checks off. DB pool and disk alerts are the hosting platform's job, and so are backups taken by the provider rather than `backup.sh` (`infra/README.md`).
- **After a database restore:** `npm run restore-reconcile` asks Keycloak about every account that can still sign in and lists the ones whose Keycloak user is gone (deleted after the backup was taken). With `--apply --by <operator> --reason "<why>"` it queues them for deletion again (audited `account.restore_repurge`); the normal purge finishes them. It changes nothing if any lookup fails, and stops when more than 5% of accounts look deleted unless `--allow-many` is given. Steps in `infra/README.md`.
- **Background jobs (Doc 17 outbox/worker rules):** account deletions, account exports and Keycloak session ends share one retry policy (`src/jobs/retry-policy.ts`): a failed attempt is retried after 1, 5, 15 and then 60 minutes; the 5th failure in a round moves the job to `dead_letter`, where it stays until an operator retries it on `/admin/jobs` (a new round of 5). Workers look for due jobs every minute. Each job records `attempts`, `next_attempt_at`, `last_error_code` (e.g. `IDP_DELETE_FAILED`, `DB_40001`, `SYS_ECONNREFUSED`; a code only, never a message, body or token) and when it was dead-lettered (migration 021). A dead-lettered **account deletion keeps the account locked** (`deleting`, every token refused), stays on `/admin/jobs`, and keeps `job_dead_letter` and `account_deletion_failed` open, with `account_deletion_late` at 25 days; Doc 17's 30-day deadline is met by an operator fixing the cause (usually Keycloak) and retrying, which the 3-a-day staff retry ceiling allows several times over. A dead-lettered export reads `failed` to the user, who can ask again; a dead-lettered session end changes nothing for the user, since the API already refuses that session. Without a Keycloak admin client no session end is attempted, so that queue is not listed or alerted.
- **Audit retention (180 days, confirmed by Tar 2026-10-04):** the API removes audit records older than 180 days once a day and records the count as `audit.retention`. On by default; `AUDIT_RETENTION_ENABLED=false` turns it off. The database still refuses every change to an audit row and every removal of a younger one; the only way to remove an old row is the session switch `tunedeck.audit_retention` that the job sets (migration 012).
- **Remote config (Doc 17 /admin/config, Doc 14):** schema version 1 has only `minSupportedBuild.ios`/`.android` (build number or null), the disable-only switches `features.catalogBrowse`, `features.playlistImport`, `features.diagnosticsUpload`, `features.radioDirectory`, `features.videoPlayback`, `features.webBrowser`, `features.carScreenVideo` (true = the build's default; false turns a shipped feature off) and `catalogRefreshHours` (1–168). Nothing else can be set, so config cannot enable hidden behavior. Releases live in the append-only `app_config_releases`; each expires (`expiresAt`), after which apps fall back to their built-in defaults. The signing key is `CONFIG_SIGNING_KEY` (Ed25519 PKCS#8 PEM, `\n`-escaped on one line is fine), required outside dev; `npm run config-key` prints a new key pair and the public key the apps pin. Dev without a key signs with a throwaway key per start.
- **Audit:** station creates, edits, publishes, disables, enables and role changes write `audit_events` in the same transaction as the change, so if the audit write fails the change rolls back. The table rejects UPDATE and DELETE.
- **Errors** use `{code, messageKey, requestId, details}` with no tokens or PII. Bodies over 16 KiB → 413.
- **Logs:** one JSON line per request (timestamp, severity, service, environment, build, eventCode, requestId, traceId, method, route template, status, durationMs, internal account id). Headers, bodies and query strings are never logged. A well-formed inbound `X-Request-Id` is reused, otherwise one is generated.
- **Trace context (W3C `traceparent`):** a valid inbound `traceparent` (version 00, lowercase hex, non-zero ids) joins that trace; anything else starts a new one. The response carries `traceparent` with the same trace id, the API's own span id and the caller's flags. Every line logged while serving the request (the request line, the error filter, rate-limit and idempotency warnings) carries `traceId`, kept in `operational_logs.trace_id` (migration 022) and searchable on `/admin/logs`. Background jobs log outside any request and have no trace id. The console BFF starts the trace for its own calls.

## Run locally

```bash
cp .env.example .env    # fill in DATABASE_URL and your Keycloak realm
npm ci
npm run build
npm run migrate         # forward-only SQL migrations in src/db/migrations
npm start               # listens on PORT (default 3100)
```

Environment keys (no secrets committed): `APP_ENV`, `BUILD_VERSION`, `PORT`, `DATABASE_URL`, `OIDC_ISSUER`, `OIDC_AUDIENCE`, `OIDC_JWKS_URI`, `OIDC_ALGORITHMS`, `KEYCLOAK_ADMIN_CLIENT_ID`, `KEYCLOAK_ADMIN_CLIENT_SECRET`, `CONFIG_SIGNING_KEY`, `AUDIT_RETENTION_ENABLED`, `STAFF_MFA_ACR`, `CORS_ALLOWED_ORIGINS`, `STATION_CHECK_ENABLED`/`_INTERVAL_MIN`/`_REGION`/`_RUNNER`, `ALERTS_ENABLED`, `ALERT_WEBHOOK_URL`, `DB_POOL_MAX`, `SHUTDOWN_DRAIN_MS`, and the store keys above.

## Migrations

`001_users_and_account_preferences.sql` creates `users` (OIDC subject, status, no password) and `account_preferences` (owner, schema version, revision, JSON value). `002_devices.sql` creates `devices` keyed by (owner, device id). `003_staff_stations_audit.sql` creates `staff_roles`, `radio_stations` and the append-only `audit_events`. `004_operational_logs.sql` creates `operational_logs`. `005_station_health.sql` creates `station_health`. `006_rate_limits.sql` creates `rate_limit_counters`. `007_client_diagnostics.sql` creates `diagnostic_reports` and `diagnostic_events`. `008_account_deletion.sql` creates `account_deletions`. `009_user_email.sql` adds the email columns. `010_app_config.sql` creates `app_config_draft` and the append-only `app_config_releases`. `011_sync.sql` creates `synced_entities`, `sync_changes`, `sync_horizons` and adds `devices.last_synced_at`. `012_audit_retention.sql` lets the retention job remove audit rows past 180 days. `013_purchases.sql` creates `purchases` and `store_notifications`. `020_device_preferences.sql` creates `device_preferences`. `021_job_retries.sql` adds the retry and dead-letter columns to `account_deletions`, `account_exports` and `devices` (open failing deletions start a fresh round; failed exports become `dead_letter`). `022_log_trace.sql` adds `operational_logs.trace_id`. `023_staff_mfa_sessions.sql` remembers which Keycloak sessions signed in with MFA. `024_rights_records.sql` creates `rights_records` and `station_rights_until()`, back-fills one record per station that had a rights basis and reference (holder `[not recorded: migrated]`, territory the station's country, valid from the station's creation date) and removes `rightsBasis`, `rightsReference` and `rightsExpiresAt` from drafts and published snapshots. `025_config_targeting.sql` adds the staging channel, targets, authors and reviewer to config releases.  `026_staff_role_scope.sql` adds `staff_roles.revoked_by` (filled by `npm run staff revoke`) and `scope` (only `global` in R1). `027_station_check_requests.sql` creates `station_check_requests` for the separate checker. `028_backup_runs.sql` creates `backup_runs`, where `infra/backup/backup.sh` records each checked dump. `029_directory_blocks.sql` creates `directory_blocks` for the community directory. Migrations are forward-only and serialized with an advisory lock; to undo, add a new migration.
