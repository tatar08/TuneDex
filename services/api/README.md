# TuneDeck API (`services/api`)

NestJS + PostgreSQL backend. This folder started as COL-01 from [Doc 19](../../Docs/19-Claude-Codex-Collaboration.md) and now holds health probes, account settings, the device registry, staff roles and the radio station catalog. It is self-contained (own `package.json` and lockfile) so it does not touch root manifests that COL-00 will define.

## What it does

| Route | Behavior |
|---|---|
| `GET /health/live` | 200 while the process runs |
| `GET /health/ready` | 200 when PostgreSQL answers, else 503 |
| `GET /v1/me/settings` | The signed-in account's settings with `ETag: "<revision>"`. New accounts get defaults at revision 0 |
| `PATCH /v1/me/settings` | Partial update. Requires `If-Match: "<revision>"`; stale → 412 `REVISION_MISMATCH` with `currentRevision` |
| `GET /v1/me/devices` | The account's devices plus the current `settingsRevision`, active first, most recently seen first |
| `PUT /v1/me/devices/{deviceId}` | The phone app's check-in: registers the device on first call, then records platform, OS major, app build and the settings revision it has applied |
| `DELETE /v1/me/devices/{deviceId}/session` | Revokes a device. Needs a sign-in within the last 5 minutes (`auth_time`), else 401 `REAUTH_REQUIRED`. The first revoke is audited as `device.revoke`. The device's Keycloak session is then ended too (see **Device sessions at Keycloak**) |
| `GET /v1/me` | Signed-in user. `{ userId, email, status, createdAt }`: the account code customers give support (looked up in `/admin/users`). The email comes from the access token's `email` claim and is stored on sign-in (cleared when the account is purged). No subject or roles |
| `POST /v1/sync/push` body `{ deviceId?, changes: [...] }` | Account sync (Doc 06), R1 scope: station favorites. Up to 100 changes `{ changeId, entityId, type: "favorite", op: "upsert"\|"delete"\|"restore", baseRevision, value: { stationId, order } }`, applied in order, each with its own result: `applied` (new `revision`), `conflict` (`exists`, `not_found`, `revision_mismatch`, `deleted`, `not_deleted`, `station_already_favorite`, with the server's `current` state) or `rejected` (`unknown_station`, `change_id_reused`). `baseRevision` 0 creates; otherwise it must equal the current revision. A delete wins over stale updates; only `restore` naming the tombstone revision brings an entity back, and a create can never reuse a deleted id. A replayed `changeId` returns its first result. One live favorite per station. A revoked `deviceId` → 403 `DEVICE_REVOKED` |
| `GET /v1/sync/pull?cursor=&limit=&deviceId=` | Changes and tombstones after the cursor, oldest first (limit 1–100, default 50), with the next `cursor` and `hasMore`. No cursor = full reconciliation. Tombstones and replay records are kept 90 days; a cursor from before the account's purged horizon → 410 `SYNC_RESET_REQUIRED` (pull again without a cursor). Push and pull with `deviceId` record the device's `lastSyncedAt` |
| `GET /v1/me/favorites` | The live favorites with their revisions, in order (for the web page) |
| `POST /v1/billing/verify` body `{ store: "apple", signedTransaction }` or `{ store: "google", productId, purchaseToken }` | The app sends the store's proof after a purchase or restore. Apple: the JWS is verified offline against the pinned Apple root (chain, validity, Apple marker extensions, ES256), then bundle id, Pro product id and environment are checked. Google: the Play Developer API is asked as the service account, then the purchase is acknowledged after it is stored. `appAccountToken` (Apple) or `obfuscatedExternalAccountId` (Google), when set, must be the account id. One purchase belongs to one live account (409 `PURCHASE_CONFLICT`); a purchase of a deleted account moves to the account restoring it. A revoked purchase stays revoked. Store not configured or unreachable → 503 and nothing new is granted. Audited `purchase.verified` / `purchase.pending` / `purchase.revoked` |
| `GET /v1/me/entitlements` | `{ pro: { apple, google }, purchases }`: Pro per store (`verified`, `pending`, `revoked`, `none`), store-scoped in R1 |
| `POST /v1/webhooks/apple` | App Store Server Notifications V2 (`signedPayload`, verified like a transaction). `REFUND` and `REVOKE` revoke the purchase. Redeliveries are recognized by `notificationUUID` |
| `POST /v1/webhooks/google` | Play real-time developer notifications via Pub/Sub push, authenticated by Google's OIDC token (audience and service account from config). Voided purchases are revoked; a pending purchase that completes is re-checked with the API, verified and acknowledged |
| `POST /v1/me/exports` | Doc 17 export job: needs a sign-in from the last 5 minutes (else 401 `REAUTH_REQUIRED`). 202 `{ id, status: "pending", requestedAt, readyAt, expiresAt }`; asking again while one is being built returns that one. Built in the background (retried up to 3 times, then `failed`) into `account_exports` (migration 017) and deleted 24 hours after the request, or with the account; audited `account.export` |
| `GET /v1/me/exports/{id}` | The job's status, the account's own only (404 otherwise). When `ready` it carries `download: { path, expiresAt }`: a link valid for 15 minutes, to prefix with the API base URL. Each read replaces the previous link |
| `GET /v1/export-downloads/{token}` | The export file (`Content-Disposition: attachment`), no sign-in needed: the unguessable link is the permission, so a phone can open it in a browser. Expired or replaced links are 404. Limited per client address like the public catalog; only a digest of the link is stored, and the route is logged without the token |
| `GET /v1/me/export` | The same data built on the spot, without a recent sign-in. Kept for existing clients; new clients use `POST /v1/me/exports`. Audited `account.export` |
| `DELETE /v1/me/account` | Starts account deletion (sign-in within 5 minutes, else 401 `REAUTH_REQUIRED`). 202 with a ticket. The account is locked (403 `ACCOUNT_DELETING`) and every device signed out at once; a purge first deletes the Keycloak user (see **Account deletion at Keycloak** below), then removes settings, devices, favorites and sync records, diagnostics and staff roles and leaves a pseudonymous `users` tombstone with the OIDC subject cut. The ticket reads `completed` only after both. Failed purges retry every 10 minutes. Tokens from sign-ins made before the request are refused |
| `GET /v1/account-deletions/{ticket}` | Public progress: `deleting`, `completed` or `failed`, with the 30-day deadline. Rate limited per client address |
| `GET /v1/me/staff` | The caller's current staff roles (empty for customers), so the console knows which pages to show |
| `POST /v1/diagnostics/batches` | Signed-in user, from one of their registered, non-revoked devices. Opt-in upload: `consent: true`, `batchId`, `deviceId` and 1-100 events in the Doc 07 schema (allowlisted names and fields only; unknown fields are refused). Up to 128 KiB, 10 batches a minute per device. Retries are safe: a repeated `batchId` returns the first result and repeated `eventId`s are skipped |
| `GET /v1/me/diagnostics`, `GET /v1/me/diagnostics/{id}`, `DELETE /v1/me/diagnostics/{id}` | The owner's own reports (summary, full events, delete). Reports are deleted after 7 days |
| `GET /v1/catalog/radio?cursor=&limit=` | Public, no sign-in. Published, enabled stations with current rights; opaque cursor, `limit` ≤100, weak ETag and `If-None-Match` → 304, `Cache-Control: public, max-age=300` |
| `GET /v1/admin/stations`, `GET /v1/admin/stations/{id}` | `catalog_editor` or `admin`. Draft, published snapshot, status, stream `health` (`unknown`/`ok`/`failing`/`suspect`, per region) and the reasons the caller could not publish right now |
| `POST /v1/admin/stations`, `PATCH /v1/admin/stations/{id}` | `catalog_editor` or `admin`. Edits the draft only; PATCH needs `If-Match` |
| `POST /v1/admin/stations/{id}/publish` | `admin`, with `If-Match` naming the reviewed revision and a `reason`. Needs recent MFA (see **Recent MFA for staff**) |
| `GET /v1/admin/stations/{id}/health` | `catalog_editor` or `admin`. The last 20 stream checks, newest first: region, time, result code, HTTP status, latency. No URLs |
| `POST /v1/admin/stations/{id}/check` | `catalog_editor` or `admin`. Checks the published stream now (the draft stream before the first publish). One manual check per station per minute (429 `CHECK_TOO_SOON`); audited as `station.check` |
| `POST /v1/admin/stations/{id}/disable`, `/enable` | `admin`, with a `reason`. Hides or restores the station in the public catalog at once |
| `GET /v1/admin/logs?from=&to=&severity=&service=&build=&eventCode=&requestId=&status=&limit=&cursor=` | `operator` or `admin`. Newest first; window ≤7 days (default last hour), `limit` ≤200, opaque cursor. Every search is written to `audit_events` before results are returned |
| `GET /v1/admin/audit?from=&to=&actor=&action=&targetType=&targetId=&requestId=&includeReads=&limit=&cursor=` | `auditor` or `admin`. Newest first; window ≤90 days (default 7), `limit` ≤200, opaque cursor. `actor` takes an OIDC subject or `operator:<label>`; `action` takes a full action or a family (`station`). Each read writes an `audit.search` row; search rows are hidden unless `includeReads=1` |
| `POST /v1/admin/audit/export?<same filters>` body `{ "reason" }` | `auditor` or `admin`. The same search as CSV (UTF-8 with BOM, formula-like cells prefixed with `'`), at most 10,000 rows (more is 400 `too_many_rows`). The reason (10–500 characters) is recorded with the filters and row count as `audit.export`. Needs recent MFA |
| `GET /v1/admin/overview?window=1h\|24h\|7d` | `operator` or `admin`. Aggregates only: request count, 5xx/4xx, p50/p95 latency and per-bucket bars from stored request logs, station health counts, account-deletion queue, and incidents (5xx ≥ 5% with ≥ 50 requests, failed or late deletions, suspect stations, stalled checker, no traffic for 15 min) |
| `GET /v1/admin/metrics?from&to&bucket=1h\|1d&method&route` | `operator` or `admin`. Doc 17 operational metrics: request counts, 5xx/4xx, error rate and latency per hour or UTC day, overall and for the 50 busiest route templates. Default the last 24 hours by hour; hourly over at most 14 days, daily over at most 90. Every 5 minutes (and before a read if older than a minute) the request log lines are rolled up into `api_metrics_hourly` (migration 018), kept 90 days, so the numbers outlive the 14-day logs. Latency is an 8-slot histogram (≤50, 100, 250, 500, 1000, 2500, 5000 ms, slower), so `p50UpToMs`/`p95UpToMs` are the upper bound of the slot holding that percentile (`null` above 5 s). Labels are method and route template only |
| `GET /v1/admin/jobs?status=open\|failed\|completed\|all` | `operator` or `admin`. Background jobs (today: account deletions) with age, attempts, last attempt and the 30-day deadline; completed ones listed for 7 days. Ids are ticket hashes, never user ids |
| `POST /v1/admin/jobs/{id}/retry` body `{ "reason" }` | `operator` or `admin`. Runs that job now under the queue lock. Idempotent (a finished job returns `completed` and runs nothing); 429 `JOB_RETRY_TOO_SOON` within 60 s of the last attempt; 409 `JOB_BUSY` while a background run holds the queue. Audited as `job.retry` with the reason and result |
| `POST /v1/admin/users/lookup` body `{ "query", "reason" }` | `support` or `admin`. Doc 17 support lookup by user id, device id or email (exact, any case; an email on more than one account is a miss): email, account status, settings revision, devices (platform, app build, last check-in, whether they applied the latest settings, revoked), diagnostics count for 7 days, deletion state. No setting values, stations or roles. Every lookup, including misses, is audited as `user.lookup` with the reason; the searched email is never written to the audit |
| `GET /v1/config` | Public, no sign-in. The newest remote config release (or the built-in defaults as release 0) as `{ jws, schemaVersion, release, publishedAt, expiresAt, config }`. `jws` is a compact JWS (EdDSA, Ed25519, header `kid` and `typ: tunedeck-config+jws`) whose payload is the same document; apps must verify it with the pinned public key and act only on its payload. `ETag`/`If-None-Match` → 304 |
| `GET /v1/admin/config` | `operator` or `admin`. The draft (with its revision as `ETag`), the current release, the last 20 releases, what changed since the release and why the viewer cannot publish |
| `PATCH /v1/admin/config/draft` | `admin`, `If-Match: "<draft revision>"`. Partial change to the allowlisted fields; unknown fields → 400. Audited `config.update` with the changed values |
| `POST /v1/admin/config/publish` body `{ "reason", "validDays"? }` | `admin`, `If-Match` = the draft revision reviewed. Two-person rule: anyone who changed the draft since the last release cannot publish it (409 `PUBLISH_BLOCKED` `own_change`). `validDays` 7–90 (default 30) sets `expiresAt`. Needs recent MFA. Audited `config.publish` |
| `POST /v1/admin/config/releases/{release}/rollback` body `{ "reason", "validDays"? }` | `admin`. Re-releases an earlier payload as a new release (history is never edited; one admin may do this alone). Needs recent MFA. Audited `config.rollback` |

- **Auth:** every `/v1` call except the public catalog needs an OIDC bearer token verified against the JWKS for issuer, audience, expiry and an asymmetric algorithm. The account comes from the token `sub`, never from the body or URL. Unknown key or bad token → 401; key set unreachable → 503 (fails closed). Accounts in `deleting`/`disabled` status → 403. There is no dev bypass; fake identity exists only in `test/`.
- **Settings allowlist** (proposal, see `openapi.proposal.yaml`): `theme` system/light/dark, `language` th/en, `cellularPolicy` allow/wifi_only. Defaults: system, th, allow.
- **Devices:** `deviceId` is a UUID the app generates once per install. Check-ins accept only `platform` (ios/android), `osMajor`, `appBuild` and `appliedSettingsRevision`; no device name, model or advertising id is stored. An applied revision higher than the server's → 400; a late, older report never moves the applied revision backwards. A revoked device's check-in → 403 `DEVICE_REVOKED` (the app should sign out). At most 20 active devices per account → 409 `DEVICE_LIMIT`. Device ids are scoped per account, so another account's id is simply not found.
- **Staff roles** (`support`, `catalog_editor`, `operator`, `admin`, `auditor`) live in the database and are read on every staff request, so a revoke takes effect on the next call. There is no self-service grant: an operator runs `DATABASE_URL=… npm run staff -- grant <oidc-subject> <role> --by <name> --reason "<why>"` (also `revoke`, `list`). Each grant and revoke is audited.
- **Station catalog:** every station has a draft and, once approved, a published snapshot; only the snapshot reaches the apps. Two-person rule: anyone who changed the draft since its last publish cannot publish it. Publishing also needs a rights basis and reference, and an expiry date that has not passed; once the expiry date passes the station drops out of the public catalog on its own. Stream URLs must be `https://` on port 443 with a public host name (no IP literals, `localhost` or internal suffixes, no credentials). The API never fetches them; health checks belong to the future worker.
- **Operational logs:** every redacted log line still goes to stdout, and is also buffered and written to `operational_logs` in batches off the request path (health probes excluded). If the database is unavailable the batch is dropped and a `LOG_STORE_DROPPED` count goes to stdout; requests are never slowed or failed by logging. Lines older than 14 days are deleted hourly in small chunks.
- **Stream health (Doc 17 catalog checker):** with `STATION_CHECK_ENABLED=true` the API checks every published, enabled station every `STATION_CHECK_INTERVAL_MIN` minutes (default 15, plus up to 10% jitter), four at a time, and only one instance runs a pass (advisory lock). Each check is HTTPS on 443 only; every DNS answer and every redirect target must be a public address (loopback, private, link-local, metadata, CGNAT, documentation, multicast and IPv6 ULA/link-local/mapped/NAT64 are refused), the connection goes to the address that was checked so DNS cannot rebind, at most 3 redirects, 10 s, and only the headers and first bytes are read. Results go to `station_health` as codes (no URLs) tagged with `STATION_CHECK_REGION`, kept 30 days. Three failures in a row since the last publish make a station `suspect` for an admin to review; nothing is disabled automatically.
- **Rate limits (Doc 17 initial limits):** a signed-in caller gets 120 reads and 30 writes a minute; the public catalog gets 60 a minute per client address. Counters are per minute in PostgreSQL (`rate_limit_counters`, unlogged), so every instance shares them; client addresses are stored only as a short hash. Over the limit is 429 `API_RATE_LIMITED` with `Retry-After`. Health probes and rejected sign-ins are not counted. If the counters cannot be written the request goes through and `RATE_LIMIT_UNAVAILABLE` is logged. Set `TRUST_PROXY_HOPS` to the number of proxies in front of the API so the client address comes from their `X-Forwarded-For`.
- **Idempotency-Key (Doc 17):** any signed-in `POST`/`PUT`/`PATCH`/`DELETE` may carry an `Idempotency-Key` header (8–128 characters of `A-Z a-z 0-9 _ . : -`, e.g. a UUID). The same account, method, path and key then runs at most once for 24 hours: a repeat with the same body and `If-Match` gets the first answer again (same status, body, `ETag` and `Location`) with `Idempotent-Replayed: true`; a repeat with a different body is 409 `IDEMPOTENCY_KEY_REUSED`; a repeat while the first is still running is 409 `IDEMPOTENCY_IN_PROGRESS` with `Retry-After: 1`. Only successful answers are kept; an error frees the key so the client can retry with it. Only digests of the key and request are stored (`idempotency_keys`, migration 016), expired keys are pruned hourly, and an account's keys are removed when it is purged. If that table cannot be reached the request is 503, not run unprotected. Requests without the header behave as before. A retried `DELETE /v1/me/account` after the first succeeded gets 403 `ACCOUNT_DELETING` (the account is locked at once), not the ticket again. `POST /v1/sync/push` also keeps its own per-change idempotency.
- **Account deletion at Keycloak** (Tar's decision A, 2026-10-04): the purge deletes the user at Keycloak (`DELETE /admin/realms/<realm>/users/<sub>`) before touching local data, using the service account of a confidential client (`KEYCLOAK_ADMIN_CLIENT_ID` / `KEYCLOAK_ADMIN_CLIENT_SECRET`, client-credentials grant). The realm and URLs come from `OIDC_ISSUER`. A user already gone (404) counts as deleted, so retries are safe; any other failure leaves the account untouched in `deleting` and is retried, logged as `ACCOUNT_PURGE_FAILED` with `errorCode` `IDP_TOKEN_FAILED` or `IDP_DELETE_FAILED` and the HTTP status only. The `account.deleted` audit records `idpUser`: `deleted`, `already_gone` or `not_configured`. Required outside dev; in dev without it the Keycloak user is kept and `IDP_USER_KEPT` is logged. Keycloak setup: create a confidential client with only "Service accounts" enabled and give its service account the `realm-management` role `manage-users` (Keycloak has no narrower built-in delete-only role; where the Keycloak version supports fine-grained admin permissions, limit it to deleting users). This assumes the realm serves TuneDeck only; a shared realm would delete the person's other logins too.
- **Store purchases (Doc 11, ADR-12):** only a SHA-256 digest of Apple's `originalTransactionId` or Google's `purchaseToken` is stored (`purchases`, migration 013), never receipts or identifiers, and they are never logged. Each store is off until configured: Apple needs `APPLE_BUNDLE_ID`, `APPLE_ROOT_CA_PEM` (Apple Root CA - G3, from apple.com/certificateauthority), `APPLE_PRO_PRODUCT_IDS` and optionally `APPLE_ENVIRONMENTS` (default `Production`); Google needs `GOOGLE_PLAY_PACKAGE_NAME`, `GOOGLE_PLAY_PRO_PRODUCT_IDS`, `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` (a service account with Play Console financial access), `GOOGLE_PUBSUB_PUSH_AUDIENCE` and `GOOGLE_PUBSUB_PUSH_SERVICE_ACCOUNT`. Staff cannot grant Pro.
- **Device sessions at Keycloak:** a device reports its token's Keycloak session id (`sid`) when it checks in (`devices.idp_session_id`, migration 014). Signing the device out from the web then ends that session at Keycloak (`DELETE /admin/realms/<realm>/sessions/<sid>`, and again with `isOffline=true` for offline tokens), so its refresh token stops working. From the moment of the revoke the API also refuses any token carrying that session id for that account (403 `DEVICE_REVOKED`), so the sign-out holds even while Keycloak is unreachable; failed calls are logged as `IDP_SESSION_END_FAILED` and retried every 10 minutes for 30 days. Other devices and the web session are not touched. It uses the same `KEYCLOAK_ADMIN_CLIENT_*` service account as account deletion (`manage-users` covers sessions). Devices that have not checked in since this release have no session id yet; their sign-out works as before (refused by device id on the API, refresh token valid until it expires).
- **Recent MFA for staff (Doc 17):** station publish, config publish, config rollback and audit export need an access token whose `acr` is one of `STAFF_MFA_ACR` and whose `auth_time` is within 5 minutes, else 401 `MFA_REQUIRED` (`details.maxAgeSeconds: 300`). Reading is unaffected. `STAFF_MFA_ACR` is required outside dev; in dev without it the check is off. Keycloak setup: an authentication flow with a step-up level that requires OTP or WebAuthn, mapped to the acr value(s) listed here (Realm settings → ACR to LoA mapping), and the console's `OIDC_MFA_ACR` set to the same value.
- **Alerts (Doc 17):** once a minute, on one instance, the API checks:
  - API 5xx above 2% of at least 100 requests in 5 minutes (critical);
  - p95 latency above 1 s over at least 20 requests in 10 minutes (warning);
  - failed account deletions (critical), deletions still pending after 5 minutes (warning), and deletions older than 25 days (critical);
  - a stream checker that stopped running (warning, only when the checker is on).
  
  Too little traffic reads "unknown" and neither opens nor closes an alert. Each occurrence is a row in `alerts` (migration 015). It is logged as `ALERT_FIRING` / `ALERT_RESOLVED` with the rule in `errorCode`, shown on `/admin/overview` with its start time, and, when `ALERT_WEBHOOK_URL` is set (https, Slack- or Discord-compatible, a secret that is never logged), posted as a Thai chat message. Failed posts are retried on the next run (`ALERT_NOTIFY_FAILED`). Messages carry aggregates only. `ALERTS_ENABLED=false` turns the checks off. DB pool, disk and backup alerts are the hosting platform's job (`infra/README.md`).
- **After a database restore:** `npm run restore-reconcile` asks Keycloak about every account that can still sign in and lists the ones whose Keycloak user is gone (deleted after the backup was taken). With `--apply --by <operator> --reason "<why>"` it queues them for deletion again (audited `account.restore_repurge`); the normal purge finishes them. It changes nothing if any lookup fails, and stops when more than 5% of accounts look deleted unless `--allow-many` is given. Steps in `infra/README.md`.
- **Audit retention (180 days, confirmed by Tar 2026-10-04):** the API removes audit records older than 180 days once a day and records the count as `audit.retention`. On by default; `AUDIT_RETENTION_ENABLED=false` turns it off. The database still refuses every change to an audit row and every removal of a younger one; the only way to remove an old row is the session switch `tunedeck.audit_retention` that the job sets (migration 012).
- **Remote config (Doc 17 /admin/config, Doc 14):** schema version 1 has only `minSupportedBuild.ios`/`.android` (build number or null), the disable-only switches `features.catalogBrowse`, `features.playlistImport`, `features.diagnosticsUpload` (true = the build's default; false turns a shipped feature off) and `catalogRefreshHours` (1–168). Nothing else can be set, so config cannot enable hidden behavior. Releases live in the append-only `app_config_releases`; each expires (`expiresAt`), after which apps fall back to their built-in defaults. The signing key is `CONFIG_SIGNING_KEY` (Ed25519 PKCS#8 PEM, `\n`-escaped on one line is fine), required outside dev; `npm run config-key` prints a new key pair and the public key the apps pin. Dev without a key signs with a throwaway key per start.
- **Audit:** station creates, edits, publishes, disables, enables and role changes write `audit_events` in the same transaction as the change, so if the audit write fails the change rolls back. The table rejects UPDATE and DELETE.
- **Errors** use `{code, messageKey, requestId, details}` with no tokens or PII. Bodies over 16 KiB → 413.
- **Logs:** one JSON line per request (timestamp, severity, service, environment, build, eventCode, requestId, method, route template, status, durationMs, internal account id). Headers, bodies and query strings are never logged. A well-formed inbound `X-Request-Id` is reused, otherwise one is generated.

## Run locally

```bash
cp .env.example .env    # fill in DATABASE_URL and your Keycloak realm
npm ci
npm run build
npm run migrate         # forward-only SQL migrations in src/db/migrations
npm start               # listens on PORT (default 3100)
```

Environment keys (no secrets committed): `APP_ENV`, `BUILD_VERSION`, `PORT`, `DATABASE_URL`, `OIDC_ISSUER`, `OIDC_AUDIENCE`, `OIDC_JWKS_URI`, `OIDC_ALGORITHMS`, `KEYCLOAK_ADMIN_CLIENT_ID`, `KEYCLOAK_ADMIN_CLIENT_SECRET`, `CONFIG_SIGNING_KEY`, `STATION_CHECK_ENABLED`, `AUDIT_RETENTION_ENABLED`, `STAFF_MFA_ACR`, `ALERTS_ENABLED`, `ALERT_WEBHOOK_URL`, and the store keys above.

## Migrations

`001_users_and_account_preferences.sql` creates `users` (OIDC subject, status, no password) and `account_preferences` (owner, schema version, revision, JSON value). `002_devices.sql` creates `devices` keyed by (owner, device id). `003_staff_stations_audit.sql` creates `staff_roles`, `radio_stations` and the append-only `audit_events`. `004_operational_logs.sql` creates `operational_logs`. `005_station_health.sql` creates `station_health`. `006_rate_limits.sql` creates `rate_limit_counters`. `007_client_diagnostics.sql` creates `diagnostic_reports` and `diagnostic_events`. `008_account_deletion.sql` creates `account_deletions`. `009_user_email.sql` adds the email columns. `010_app_config.sql` creates `app_config_draft` and the append-only `app_config_releases`. `011_sync.sql` creates `synced_entities`, `sync_changes`, `sync_horizons` and adds `devices.last_synced_at`. `012_audit_retention.sql` lets the retention job remove audit rows past 180 days. `013_purchases.sql` creates `purchases` and `store_notifications`. Migrations are forward-only and serialized with an advisory lock; to undo, add a new migration.

## Not in this slice

CSRF/BFF (COL-03), per-device preference overrides, staff session limits beyond the console's, support-role access to diagnostics, log export and multiple stream variants per station, audit outbox, metrics/traces, Dockerfile and CI. Shared OpenAPI, root scripts and CI belong to COL-00.
